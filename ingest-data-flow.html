Read the two shaded rows carefully — they are the only writers that bypass Django's signal pipeline: the Go Dentally sync re-implements Person/channel resolution (E.164 + lowercase, twin adoption) in Go, and the Call Agent's GORM intake insert skips set_patient_person entirely (the Person link is established by the follow-up Django notification instead). Every other row, no matter the language, funnels through the signal pipeline and therefore the canonical chokepoint.

The two chokepoints every Django-side write eventually passes

1 · ContactChannel.get_or_create_channel (models.py:219) — "the ONE chokepoint for a contact channel WRITE": phone → canonical_phone_e164 (practice default as last-resort region; non-E.164 stored as bare digits with needs_review=True), email → strip+lower. A _canonical_twin adoption reuses an existing E.164 channel instead of minting a bare-digit duplicate.
2 · contact/signals.py auto-linking — pre/post-save on every Patient / Intake / Nurture save (regardless of entry point): _ensure_channels → Person.resolve (name + DOB + channels) → Person, PersonChannel, Household (family grouping). Messaging additionally back-fills session names from the resolved Person.

The residual gaps are (a) onlineBooking writing fully raw contact columns, (b) archive restores inheriting pre-canonical values, and (c) a one-off migration to canonicalise existing Patient.phone_number/email columns would make stored data itself uniform.

Id-space rule: person_id, Patient.id, and Dentally patient_id are three different number spaces — consumers added since 2026-09-02 (family picker, household endpoint, conversion matcher, Link-step search) all key off the correct one.
