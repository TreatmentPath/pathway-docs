The identity core

A Person is one human. A ContactChannel is one phone number or email address. A Household is a family — several distinct Persons. Sharing a phone is a household signal, never an identity signal.

Two routes to a human

Nothing else stores a person's identity. It either hangs off a Patient row or off a ContactChannel — which is why re-pointing those two carries most of the system with it.

  MSG["Email · SMS
Calls · Conversations"] --> C["ContactChannel"]
  P --> PER["Person"]
  C --> PC["PersonChannel"] --> PER
  PER --> H["Household"]
Why this matters for merging. Re-point Patient and the channels, and treatment plans, appointments and every conversation follow automatically — they never stored a person in the first place.

What points at Patient 40 FKs · 16 apps

A patient row holds only that person's own 41 columns — name, contact details, dates. Everything else lives in its own table with a patient_id written on it. Delete a patient row and those rows point at nothing, which is why deduplication has to re-point before it deletes. The recurring bug. Both Person.merge and migration 0140 listed these tables by hand. A hand-written list is only ever correct for the day it was written — 0140 named three tables and hit nine in production. Ask the database instead.

Draw any slice yourself

django-extensions and Graphviz are both already installed. graph_models can't write images directly here (no pygraphviz), so emit a .dot file and render it with dot. 

# from TreatmentPathBackend/TreatmentPath, venv active

# one slice — pick the models you care about
python manage.py graph_models TreatmentPlan \
  --include-models "Person,PersonChannel,ContactChannel,Household,Patient,Intake,Nurture" \
  --dot -o identity.dot
dot -Tsvg identity.dot -o identity.svg

# a whole app
python manage.py graph_models patient_accounts --dot -o accounts.dot
dot -Tsvg accounts.dot -o accounts.svg

# everything (465 models — expect an unreadable wall; slice instead)
python manage.py graph_models --all-applications --dot -o all.dot
Slice by app or by model list. One diagram of all 465 models and 1,071 foreign keys is not a diagram — it's a hairball. The useful question is always "what touches this".
